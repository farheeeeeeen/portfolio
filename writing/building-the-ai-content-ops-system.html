Building EquityList's AI Content Operations System

I lead content strategy at EquityList with no engineering background. This is how I used Claude Code to build a working operations system for quarterly planning, weekly SEO and lead analysis, and content ops — the bugs I caught by actually using it, and the framework I found out I'd already built.

The job before this system was the ordinary content-marketer grind. Track a growing blog inventory by hand. Guess at keyword volumes. Pull Search Console and HubSpot exports one at a time. Build the quarter's calendar in a spreadsheet. There was no systematic way to answer "have we already covered this?" against 150-plus posts — you searched your memory, or you searched the spreadsheet, and hoped you searched it right.

I write for founders, CFOs, and HR/People Ops at Indian startups, Seed through Series C, expanding into the US. EquityList is an equity-management platform — cap tables, ESOPs, fundraising, compliance. None of that work needs a marketer who codes. It needed a system, and I built one with Claude Code and a layer of custom Skills on top of it: reusable, plain-English-triggered workflows that turned the spreadsheet grind into something I could just talk to.

Day zero wasn't a live build

I want to be honest about how this started, because "I built this from scratch on stream" is a better story than the true one. The initial commit landed the whole skeleton at once: five skills, one sub-agent, eighteen Python scripts, and the full data layer — blog inventory, keyword map, competitor data, HubSpot snapshots, the Q2 calendar, thirty-plus weeks of pre-existing performance history. That was the first working version. Everything from there was refinement, done in the open, against real use.

The refinements started the same day. I fixed the keyword-discovery workflow because it wasn't preserving status between runs, and made the calendar paths dynamic instead of hardcoded to one quarter. A day later I extended the performance-analysis skill to pull HubSpot lead-journey data too, merging SEO performance and lead attribution into one report instead of two. A day after that, a full systems document — every script, every skill, every design decision, written in two passes, with a step-by-step section on replicating the whole thing for another company.

What it looks like today

The system has four layers. Skills sit on top — the natural-language commands I actually type. Below that, a sub-agent handles research that would otherwise clutter the main conversation. Below that, eighteen-plus Python scripts do the orchestration: hitting APIs, processing data, syncing to Sheets. At the bottom, a data layer — JSON for anything nested and stateful, CSV for anything flat and meant to be opened in a spreadsheet. All of it reads from HubSpot, Google Search Console, Plausible, Semrush, and Webflow, and writes out to Google Sheets.

Five skills carry the actual work:

  • /categorize-blogs — turns a raw list of titles and URLs into a structured inventory: category, funnel stage, geography, content type, status.
  • /content-strategy — the quarterly planning engine. Gap analysis, then competitor research (spawned as a sub-agent so it doesn't bloat the main conversation), then keyword discovery across forty-plus seed terms, then seven mandatory quality filters, then volume validation, then prioritization, then a ranked calendar of thirty-six to fifty topics.
  • /analyze-performance — the weekly report. Search Console data merged with HubSpot deal data, producing quick wins, underperformer diagnoses, internal-linking suggestions, and an automated lead-journey pull.
  • /new-blog-published — the post-publish checklist, automated: add to inventory, register the keyword, flip the calendar status from Planned to Published, suggest internal links.
  • /lead-magnets — scans for keywords that imply a tool or template rather than a blog post, scores the opportunity, and outputs a build brief.

Where the judgment actually lives

The quarterly-planning skill is the one that matters most, and the seven quality filters inside it are the closest thing this system has to my own editorial brain, written down as rules a machine can enforce every time:

Quality filters — /content-strategy
  • Audience match — would a founder or CFO actually search this, not an employee or a retail trader?
  • Domain relevance — is it actually about equity management, not generic startup advice?
  • Intent specificity — does the volume come from the right audience? "Capital gain tax on sale of shares" is mostly retail traders; the real target is "capital gains on unlisted shares."
  • Terminology accuracy — reject a topic built around a technically wrong term, even if that term has more search volume.
  • No duplication — check the existing inventory and keyword status before ever suggesting a topic twice.
  • Lead-magnet intent — a keyword implying "calculator" or "template" doesn't belong in the content calendar at all.
  • Factual currency — reject topics built on laws that have since changed.

Every one of those came from a mistake I'd already made by hand, at some point, before the system existed. Writing them down as filters didn't just save time — it meant the mistake couldn't recur silently. That's the actual value of encoding judgment into a system: it prevents the same error from happening twice.

Catching my own mistakes, in public

The honest version of this story includes the bugs, because the bugs are the proof the system was load-bearing rather than a demo. Three, specifically. The funnel analysis reported fifteen deals stuck at MQL when the real number was twenty-eight — caught by actually reading the report against what I knew from HubSpot, not by code review. The keyword-discovery workflow wasn't preserving status between runs, and the calendar paths were hardcoded to a single quarter — both caught and fixed the same day the system first shipped. A month later, the month-on-month and quarter-on-quarter performance calculations turned out to be wrong too, caught the same way: someone actually used the numbers for a decision, and the numbers didn't hold up.

Building fast with AI doesn't remove the need for a rigorous human checking the math. It just moves where that checking happens — from writing the code yourself to reading the output like you don't trust it yet. I don't trust it yet, on principle. That's what caught all three of these.

What a week looks like now

Two automations run without me touching anything. Monday at 9am, a HubSpot inbound-lead journey report lands in a new Google Sheets tab, tracking every inbound contact — web-tracked and CRM-only — since the previous Monday. Monday at 10am, the inbound funnel analysis follows: stage breakdown, conversion rates against targets, stalled-deal alerts, written specifically so a non-technical marketing lead can read it unassisted and know what to do next.

One thing is deliberately not automated: syncing the content calendar to Google Sheets requires an explicit flag. The sheet has manual formatting layered on top of it — red for rejected, strikethrough for removed — and a blind auto-sync would wipe that out. Leaving a step manual, on purpose, was the harder design call to make than automating it would have been.

A few other decisions came from the same instinct — build for what the moment actually needs, not what's easiest to automate:

  • Query scripts instead of reading raw files. The blog inventory alone is over 100KB of JSON; loading all of it into a conversation burns tokens that should go toward analysis. A single query answers "do we already have this?" instead. It's a hard rule in the project's own instructions now: never read the full inventory file.
  • Snapshots over live queries for HubSpot. Pulling live every time risks rate limits and results that don't match week to week. Weekly JSON snapshots go stale slower than they cause problems, and they're reproducible.
  • A status field — active, planned, rejected, researched — on every keyword, so the system never re-proposes something already ruled out, and "why didn't we write about X" always has a documented answer.

Finding out I'd already built the framework

A month after the system was already in daily use, I came across a post describing a four-layer architecture for AI-driven go-to-market work: a System of Context (markdown encoding ICP, competitors, positioning), a System of Skills (specialized tools per function), a System of Orchestration (agents coordinating which skills run), and a System of Integrations (the APIs to data sources and destinations).

I read it and realized my system already mapped onto all four layers, built independently, before I'd seen the framework named. Context was the project's own configuration files. Skills were the five workflows above. Orchestration was the sub-agent. Integrations were HubSpot, Semrush, Search Console, Plausible, Webflow, and Sheets.

I built this to solve my own problem, and only afterward found out it matched a framework other people were publishing about.

That's a better validation than any metric, because it means the shape of the system wasn't arbitrary — it was the shape the problem actually required, and someone else had arrived at the same shape from a different direction.

What the real deliverable was

The same method got reused recently for a different product line entirely — scoping content strategy for EquityList's secretarial-compliance product, a different surface, same underlying company. The reuse formalized into a repeatable eight-step narrowing cycle: map the full surface area before touching keywords, stress-test the lifecycle, validate volumes, apply inclusion filters, classify every rejected topic with a reason, reconcile keyword-gated against moment-gated views, tag, and route anything that isn't content to an off-blog asset instead.

That's the part I'd point to if someone asked what this project actually produced. Not the eighteen scripts or the five skills — those are the current implementation, and implementations change. What carried over to a second product was the method: a repeatable way of turning judgment calls I used to make one at a time, from memory, into something written down, checked, and reusable. The system was never really the deliverable. The judgment encoded inside it was.
